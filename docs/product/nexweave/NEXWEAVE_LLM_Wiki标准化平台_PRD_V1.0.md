## 1. 产品背景

企业中大量高价值知识长期存在于 PDF、Word、报告、工单、会议纪要、制度、专家笔记和业务系统记录中，存在以下共性问题：

1. **资料分散**：知识跨系统、跨文件、跨人员沉淀，难以形成统一入口。
2. **知识不可计算**：传统文档适合阅读，但缺少标准实体、关系、主张和证据结构，无法被业务系统稳定调用。
3. **RAG 结果不稳定**：仅依赖文档切片和向量检索，容易遗漏上下文、混淆版本、引用不准确。
4. **专家经验难传承**：经验存在于个人判断和非结构化报告中，难以复用、审核和持续更新。
5. **AI 生成不可控**：通用大模型可能产生幻觉，缺少来源、审核、版本和责任闭环。
6. **项目重复建设**：不同业务项目分别建设知识库、问答、图谱和审核功能，造成重复投入。

NEXWEAVE 以 LLM Wiki 思路为核心，将企业原始资料持续“编译”为结构化、可链接、可审核、可发布、可调用的知识资产，形成标准平台 + 领域知识包 + 业务应用的产品体系。

## 2. 产品定位

### 2.1 一句话定位

NEXWEAVE 是一个面向企业专业知识的 **LLM 原生知识编译、审核、发布与服务平台**。

### 2.2 产品不是

- 不是单纯的文档管理系统；
- 不是仅支持问答的 RAG 知识库；
- 不是 Obsidian 的企业版；
- 不是某个行业写死的故障诊断系统；
- 不是由大模型直接替代专家做最终决策的黑盒工具。

### 2.3 产品价值

NEXWEAVE 将“资料”转化为四类可复用资产：

1. 面向人的 Wiki 页面；
2. 面向机器的实体、关系、主张和证据；
3. 面向业务系统的正式知识版本与 API；
4. 面向领域应用的知识包、规则和标准问题集。

## 5. 核心设计原则

1. **Raw First**：原始资料为事实源，LLM 不得修改原文。
2. **Schema Before Generation**：先定义知识结构，再让模型生成知识。
3. **Evidence Native**：关键知识必须绑定来源、页码或段落。
4. **Human in the Loop**：正式知识必须经过人工审核。
5. **Draft / Release Separation**：草稿知识与生产知识严格隔离。
6. **Version Reproducibility**：历史回答可还原所使用的知识版本。
7. **Conflict Instead of Overwrite**：资料冲突生成待处理事项，不自动覆盖。
8. **Platform / Domain Decoupling**：平台核心不写死行业对象。
9. **Open Integration**：通过连接器、API、SDK 和领域包扩展。
10. **Security by Default**：私有化、权限隔离、日志审计和模型调用边界默认开启。

## 6. 核心业务闭环

```text
创建知识空间
  → 配置或安装领域包
  → 导入原始资料
  → 文档解析与切分
  → LLM 提取实体/关系/主张/证据
  → 自动创建或更新 Wiki
  → 同义词消歧与冲突识别
  → 知识工程师初审
  → 领域专家复核
  → Lint 与标准问题集评估
  → 发布正式知识版本
  → 问答/API/业务应用调用
  → 用户反馈与新资料触发增量更新
```

### 9.2 关系类型

### 9.3 核心页面模板

- 设备页面；
- 故障模式页面；
- 根本原因页面；
- 历史案例页面；
- 验证方法页面；
- 纠正措施页面。

### 9.4 标准问题集示例

- 某类设备出现某组现象时，可能涉及哪些候选原因？
- 哪些证据支持或反对某个候选根因？
- 如何进一步验证该候选原因？
- 是否存在同类设备的相似历史案例？
- 当前资料是否足以形成结论？
- 哪些结论存在来源冲突？

### 9.5 与生产 RCA 系统边界

NEXWEAVE RCA Pack 负责生产可信知识，不负责直接接管实时监测和最终工程决策。正式 RCA 应用可通过 API 调用已发布知识，结合实时数据、规则和人工确认完成诊断。

## 11. 技术架构建议

### 11.1 总体

```text
Web / Obsidian / API Client
        ↓
API Gateway & IAM
        ↓
Knowledge Workspace Service
Source & Parsing Service
Schema Service
LLM Compile Orchestrator
Wiki Service
Claim & Evidence Service
Review Workflow Service
Quality Evaluation Service
Release Service
Query & Retrieval Service
Integration Service
        ↓
Relational DB / Object Storage / Search / Vector / Graph / Git
        ↓
LLM Gateway / Embedding / OCR / Document Parser
```

### 11.2 技术建议

- 前端：React + TypeScript；
- 平台后端：Java/Spring Boot 或企业标准技术栈；
- LLM 编排与文档处理：Python 服务，可通过统一网关调用；
- 关系数据库：PostgreSQL/达梦适配；
- 搜索：OpenSearch/Elasticsearch 适配；
- 向量：pgvector/Milvus 适配；
- 图谱：初期关系表 + 图查询服务，后续适配 Neo4j/NebulaGraph；
- 对象存储：MinIO/S3；
- 版本：Git 或内部版本服务；
- 任务：消息队列 + 工作流引擎；
- 部署：容器化、私有化、国产化环境适配。

### 11.3 核心工程约束

- 核心领域模型不得依赖具体行业；
- Domain Pack 通过声明式配置扩展；
- 模型服务通过统一 Model Gateway 适配；
- 连接器通过插件 SPI 扩展；
- 正式知识与草稿知识物理或逻辑隔离；
- 所有引用必须可定位到原始资料；
- 高风险动作必须人工批准。

## 12. 非功能需求

### 12.1 性能

- 普通页面操作 ≤ 1 秒；
- 关键词/属性查询 ≤ 2 秒；
- 混合检索平均 ≤ 3 秒；
- 单篇 Wiki 页面打开 ≤ 2 秒；
- 大模型编译采用异步任务；
- 任务进度更新延迟 ≤ 3 秒；
- 支持至少 100 万实体、500 万关系的横向扩展设计。

### 12.2 可用性

- 核心服务可用性目标 ≥ 99.9%；
- 编译任务支持断点续跑；
- 发布操作支持回滚；
- 原始资料和正式版本支持备份恢复。

### 12.3 安全

- 私有化部署；
- HTTPS；
- RBAC + 数据权限；
- 密级和空间隔离；
- 模型调用内容脱敏；
- 第三方模型默认禁止接触高密级资料；
- 完整审计日志；
- 敏感文件禁止外发；
- API 密钥加密存储；
- 安全扫描和依赖清单。

### 12.4 可解释与可审计

- 每条关键结论可追溯来源；
- 每次 AI 生成可追溯模型和 Prompt；
- 每次审核和发布可追溯人员；
- 每次问答记录使用知识版本和引用；

### 12.5 兼容性

## 18. 验收标准

### 18.1 功能验收

- 从上传资料到发布知识版本形成完整闭环；
- 页面、实体、关系、主张和证据均可追溯；
- 草稿内容未经审核不能进入正式查询；
- 冲突可识别、分派、处理并保留记录；
- 发布版本可回滚；
- 问答结果展示引用和版本。

### 18.2 质量验收

- 发布知识来源可追溯率 100%；
- 发布页面 Schema 合规率 100%；
- 引用定位准确率达到试点约定指标；
- 标准问题集覆盖率达到试点约定指标；
- 历史回答可按版本复现；
- AI 生成内容可展示修改比例和专家接受率。

### 18.3 原型验收

高保真原型应覆盖全部一级导航，并至少完成以下可交互闭环：

- 切换知识空间；
- 上传资料；
- 启动编译；
- 查看 Wiki；
- 编辑 Schema；
- 审核知识；
- 处理冲突；
- 发布版本；
- 进行带引用问答；

## 21. 结论

NEXWEAVE 的产品核心不是“让 AI 阅读更多文件”，而是建立企业知识从原始资料到正式知识服务的标准生产线：

> **资料导入 → 知识编译 → 证据绑定 → 专家审核 → 质量评估 → 版本发布 → 业务调用。**

通过平台与领域包解耦，首期以设备缺陷 RCA 验证价值，后续可复制到智慧消防、技术监督、合同审核、电力交易、运筹优化等专业知识场景。
