# NEXWEAVE M9-FE：前端设计系统与高保真原型对齐重构任务书

> 产品：NEXWEAVE｜织界——企业级 LLM Wiki 标准化平台  
> 所属阶段：R1 / M9 补充前端整治任务，不构成 M10  
> 执行模型：`gpt-5.6-sol`  
> 推理强度：`high`  
> 建议周期：3—4 周  
> 执行对象：Codex  
> 文档状态：已正式下发；实施、独立审查修复与本地技术验收完成，待用户验收  
> 阶段原则：完成前端对齐、独立审查和验收后停止，不进入 M10

---

## 1. 任务定位

当前 React 前端已承载 M1—M9 真实 API、权限、路由和业务状态，但整体视觉语言、信息层级、页面密度、组件形态和交互细节与《NEXWEAVE 高保真交互原型 V1.0》存在系统性偏差。

本任务要在不损害现有业务真实性的前提下，重建可复用设计系统，使全部已实现页面回归 NEXWEAVE 深色知识操作系统设计语言，并建立可持续防止视觉回归的验证基线。

本任务是前端架构与体验整治，不是新业务功能 Milestone，不得修改 M1—M9 已验收的业务语义。

---

## 2. 权威输入与优先级

执行前按以下顺序读取并遵循：

1. 用户当前明确指令；
2. 已批准的 M9 任务书及 ADR-0029/0030；
3. 本任务书；
4. 仓库根目录 `AGENTS.md`；
5. `docs/product/nexweave/NEXWEAVE_高保真交互原型_V1.0.html`；
6. 已接受 ADR、`ARCHITECTURE_BASELINE.md`、`PRODUCT_BASELINE.md`和需求追踪矩阵；
7. 现有 `apps/web` 真实实现、测试和 API 契约。

冲突处理原则：

- 业务语义、权限、状态和数据来自真实实现与已验收契约；
- 信息架构、视觉语言和交互目标以高保真原型为基线；
- 原型中的静态文案、假数据、Mock 状态和演示操作不得写入真实产品；
- 无法兼容时，记录到 `OPEN_QUESTIONS.md` 并停止受影响实现，不得静默选择。

1. 盘点当前工作区和用户未提交修改，不覆盖、重置或删除任何既有工作；
2. 记录当前 Web 的 format、lint、typecheck、test 和 build 基线；

## 5. 阶段目标

1. 建立唯一、可复用、可检查的 NEXWEAVE 前端设计系统；
2. 还原高保真原型的深黑底色、紫/青/荧光绿强调色、多层面板、紧凑信息密度和知识工作台气质；
3. 将应用 Shell、基础组件和所有已实现页面迁移到统一设计基线；
4. 拆分过大组件和全局样式，降低页面间 CSS 泄漏和视觉漂移；
5. 保留已验收的 API、路由、权限、幂等、错误、加载、空状态和刷新恢复语义；
6. 建立可重复的视觉截图和功能回归验证；
7. 满足键盘可用、焦点可见、对比度、减少动画和响应式基线。

1. 不得将原型的 Mock 数据、固定 KPI、静态状态或演示文案冒充真实功能；

10. 不得自动 commit、push、创建远程 PR 或进入 M10。

## 7. FE-0：设计系统与迁移决策冻结

编码前必须产出并冻结以下内容：

### 7.1 页面与模式映射

- 建立现有路由→原型页面→真实 API→关键状态的映射矩阵；
- 将页面归并为 Dashboard、List/Detail、Workbench、Canvas/Graph、Review/Diff、Admin/Form 等界面模式；
- 标记原型中不对应真实能力的页面元素，明确不实现或改为真实状态。

### 7.2 设计 token

至少冻结：

- 颜色：背景层级、面板层级、边界、主文字、次文字、紫/青/荧光绿强调色及成功/警告/错误/信息语义色；
- 字体：中英文字体栈、字号、字重、行高、字段宽度和数据/代码字体；
- 间距：4px 基准网格及页面、面板、表单、表格、密集列表节奏；
- 形态：圆角、边框、阴影、透明度、模糊、分隔线、图标尺寸；
- 布局：侧边栏、顶栏、内容宽度、工作台分栏、右侧属性/证据面板；
- 动效：时长、缓动、hover/focus/pressed/loading，并支持 `prefers-reduced-motion`；
- 层级：z-index、浮层、Modal、Toast、Dropdown 和粘性区域。

所有视觉颜色应通过设计 token 使用；业务图表或数据可视化的动态颜色需另行受控定义。

### 7.3 组件契约

至少定义：

- AppShell、Sidebar、Topbar、PageHeader、ContentRegion；
- Button、IconButton、Input、Select、Textarea、Checkbox、Switch、Tabs、SegmentedControl；
- Panel、Card、Metric、Badge、StatusPill、Table、ListRow、Toolbar；
- Modal、Drawer、Popover、Tooltip、Toast；
- Loading、Skeleton、EmptyState、ErrorState、PermissionDenied、StaleState；
- SplitPane、WorkbenchLayout、InspectorPanel、EvidencePanel、GraphSurface、DocumentSurface；
- 可访问性属性、键盘操作、焦点管理、不可用状态和长文本约束。

### 7.4 图标与依赖策略

- 优先复用现有依赖和 CSS 能力；
- 若需引入图标、截图或可视化测试依赖，必须记录用途、固定版本、许可证、供应链风险、替代方案和删除方案；
- 不得引入一套完整组件库后强制把产品改成其默认风格；
- 不得使用远程字体、远程图片或运行时 CDN 作为内网基线。

### 7.5 迁移计划

- 明确新旧组件的过渡边界，避免长时间两套主题并存；
- 按“Shell → 样板页 → 业务页 → 特殊画布 → 清理旧样式”顺序实施；
- 列出需要拆分的过大文件和预期责任边界；
- 为每个批次定义可独立回归的停止点。

FE-0 产物需落入版本化文档，不得只保留在对话中。

## 8. 实施阶段

### FE-1：设计系统基础与 App Shell

1. 建立分层设计 token，移除当前主导的单一深绿色主题；
2. 实现与原型对齐的 Sidebar、Space Switcher、Topbar、Global Search 容器、状态和用户区域；
3. 保留现有路由、登录、空间恢复、权限可见性和退出逻辑；
4. 建立共享基础组件，并配套单元/组件测试；
5. 将全局样式拆分为 token、foundation、layout、component 和 feature 层，具体文件结构可根据仓库现状决定。

### FE-2：代表性样板页

先完成以下界面模式，作为后续迁移权威样板：

1. 总览：验证 KPI、密集信息、活动和快捷入口；
2. 资料中心：验证工具栏、列表/详情、上传、解析状态和长任务；
3. Wiki 工作台：验证三栏布局、文档表面、属性和 Evidence 侧栏；
4. Schema Studio 或图谱：验证画布、工具栏、节点和属性检查器。

每个样板页必须：

- 使用真实 API 和真实状态；
- 在三类视口渲染并检查；
- 覆盖正常、空、加载、错误、禁用和权限不足状态；
- 通过功能回归后才可作为批量迁移样板。

### FE-3：全页面迁移

将所有已实现路由迁移到统一基线，至少包括：

- 登录、总览、知识空间、平台管理；
- 资料中心、任务中心、编译中心；
- Schema Studio、Domain Pack、Wiki 工作台、Wiki 链接图；
- Claim/Evidence、冲突中心、审核中心；
- 质量中心、发布中心、Release Graph、Ask NEXWEAVE；
- 集成中心及 M9 已授权实现的前端增量。

迁移时必须同步处理：

- 页面头、工具栏、筛选、表格、详情、侧栏、弹窗和通知的一致性；
- 长名称、长错误、长引用、大数值和极端列表的布局稳定性；
- 深链接、刷新恢复、浏览器返回和选中状态；
- 不同角色、密级、空间和业务状态下的服务端权限结果展示；
- 触控、键盘、hover 不可用设备和减少动画模式。

### FE-4：结构治理与旧样式清理

1. 拆分过大组件，使路由编排、数据加载、业务操作和展示组件责任可区分；
2. 清除已不再使用的绿色主题样式、重复选择器、死 CSS 和页面级组件副本；
3. 保持类型安全，不通过 `any`、空实现或关闭规则使构建通过；
4. 未经充分理由不改变 React/Vite/TypeScript 基础技术栈；
5. 不把所有样式继续堆积到单一全局 CSS 文件。

### FE-5：独立审查、修复与验收

1. 以审查者角色重新对照原型、FE-0 决策和当前渲染结果；
2. 进行信息架构、视觉层级、一致性、响应式、可访问性和真实状态审查；
3. 检查是否遗留 Mock、硬编码颜色、重复组件、样式泄漏、不可达交互或隐藏错误；
4. 修复所有 P0/P1 视觉、功能、权限和可访问性问题；
5. 复跑完整前端门禁和与前端改动有关的真实 E2E；
6. 输出验收报告和截图证据，然后停止。

## 9. 视觉与交互强制要求

1. 整体必须呈现专业、密集、可扫读、面向重复操作的企业知识工具，不得做成营销站；
2. 品牌色以原型的深黑、紫、青和荧光绿为基线，状态色必须保持语义区分；
3. 控制卡片使用，页面分区优先通过布局、边界和层级表达，不得层层套卡；
4. 桌面端保持原型的工作台密度，但必须为窄屏重排，不得简单缩小所有字体；
5. 按钮、图标、菜单、Tabs、Segmented Control、Switch 等须使用用户熟悉的交互形态；
6. 不在产品界面内显示给开发者的使用说明、设计意图或键盘提示文案，除非它是真实帮助内容；
7. 所有文字、图标、控件、图表和画布在目标视口不得重叠、裁切或导致无法操作；
8. 所有数据界面都必须有空、加载、错误、部分成功、过期/冲突和重试表达；
9. 有破坏性、审批、发布、回滚、废止或冲突处置的操作必须保留正确强度、确认和权限语义；
10. 原型是设计基线而非像素级强制复制；为真实数据、可访问性和响应式做的偏离必须记录理由。

---

## 10. 代码与架构要求

1. 设计 token 和基础组件必须有唯一权威定义；
2. 页面优先组合共享组件，不得通过复制 JSX/CSS 维持表面一致；
3. 数据请求、业务状态和呈现组件应保持可测试边界；
4. 不得在组件中直接伪造 API 数据或静默回退到固定 JSON；
5. 保留现有 ETag、Idempotency-Key、tenant/space、clearance、状态机和服务端错误的前端传递；
6. 路由 URL 是可恢复状态的一部分，不得回退到仅内存导航；
7. 新依赖必须遵守锁版、许可证、供应链和替代方案记录；
8. 修改公共 API、业务状态或路由契约时，必须先按治理规则更新 ADR/契约；若仅为达到视觉效果而修改后端，应停止并重新设计前端方案。

## 11. 测试与验证

### 11.1 自动化门禁

至少执行：

- Prettier format check；
- ESLint；
- TypeScript strict typecheck；
- Vitest 全量前端测试；
- production build；
- 受影响的 Python/API/契约测试，若本任务不涉及后端应明确说明；
- 与关键页面相关的真实 API/Compose 冒烟或 E2E。

不得通过删除测试、降低断言、关闭 lint/typecheck 或过度 Mock 让门禁通过。

### 11.2 视觉验证

对所有主路由至少执行：

- 1440×900 宽屏桌面；
- 1024×768 紧凑桌面/平板；
- 390×844 移动窄屏；
- 浅/深不必同时实现，但 NEXWEAVE 深色主题必须完整；
- 中文长文本、英文长 ID、空数据、极端数值和错误信息；
- 导航、弹窗、Dropdown、Tooltip、Toast、Drawer 的层级和裁切；
- 可聚焦顺序、焦点可见性、键盘操作和减少动画。

截图必须使用稳定、可复现的数据状态。若引入 Playwright 或其他新工具，必须纳入依赖治理。

### 11.3 功能不变验证

至少确认：

- 登录、退出、空间切换和页面恢复正常；
- 所有已验收路由可达，且浏览器返回/前进正常；
- 服务端权限拒绝和密级拒绝没有被前端隐藏或改为成功；
- 创建、编辑、审核、发布、回滚、冲突处置和问答保留原状态机与确认；
- loading、partial、error、retry、stale、conflict 等状态不被“美化”为假成功；
- 真实 API 响应和审计行为不变。

## 14. 风险与停止规则

### P0 停止条件

出现以下任一情况，停止受影响实现：

- 需要修改后端业务语义才能实现视觉效果；
- 原型与已验收真实业务契约直接冲突；
- 重构会覆盖用户当前 M9 未提交工作；
- 必须引入未受控远程资源、不兼容许可证依赖或不可内网部署能力；
- 设计决策会实质进入 M10 或未授权业务范围。

### 可记录后继续的情况

- 原型因静态 Mock 无法体现真实错误或长任务状态；
- 为响应式、长文本或可访问性进行可说明的布局调整；
- 当前浏览器工具不能执行稳定像素差异，但已保留可检查截图和人工审查证据；
- 某个原型控件在真实实现中已被更完整的受测业务交互取代。
